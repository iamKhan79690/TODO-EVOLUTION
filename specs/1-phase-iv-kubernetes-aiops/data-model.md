# Data Model: Phase IV - Kubernetes AI-Assisted Deployment

**Feature**: 1-phase-iv-kubernetes-aiops
**Created**: 2025-12-23
**Status**: Final

## Overview

This document defines the key entities and resources for the Phase IV Kubernetes deployment. Unlike application features that define database models, this infrastructure phase defines Kubernetes resources, container images, and configuration entities.

## Core Entities

### 1. Container Image

**Description**: Docker image built by Gordon from application source code.

**Attributes**:
- `name`: Image identifier (e.g., `todo-frontend`, `todo-backend`, `todo-mcp-server`)
- `tag`: Semantic version (e.g., `1.0.0`) - never uses `latest`
- `registry`: Docker registry (local for Minikube deployment)
- `size`: Image size in MB (target: < 500MB per image)
- `base_image`: Parent image (node:18-alpine, python:3.13-slim)
- `build_context`: Source directory for Docker build
- `dockerfile`: Generated by Gordon (multi-stage build)
- `health_check`: HTTP endpoint for liveness/readiness probes

**Relationships**:
- Container Image → Deployment: One image used by one or more deployments
- Container Image → Build: Created from build context using Gordon

**Validation Rules**:
- Tag MUST follow semantic versioning (MAJOR.MINOR.PATCH)
- Base image MUST use specific version tag (no `latest`)
- MUST include non-root user (UID 1000)
- MUST include health check endpoint

---

### 2. Kubernetes Deployment

**Description**: Declarative YAML describing pod replicas, updates, and rollback strategy.

**Attributes**:
- `name`: Deployment name (e.g., `todo-evolution-frontend`)
- `namespace`: Kubernetes namespace (default for local deployment)
- `replicas`: Number of pod instances (frontend: 2, backend: 2, mcp: 1)
- `selector`: Label selector for pods (`app: todo-evolution`, `component: <type>`)
- `strategy`: Update strategy (RollingUpdate with maxSurge: 1, maxUnavailable: 0)
- `revision_history_limit`: Number of old ReplicaSets to keep (10)
- `progress_deadline_seconds`: Deployment timeout (600s)

**Pod Template Attributes**:
- `containers`: List of container definitions
- `security_context`: Pod-level security settings
- `restart_policy`: Always (for deployments)

**Container Attributes**:
- `name`: Container name (matching component)
- `image`: Container image reference
- `ports`: List of exposed ports
- `env`: Environment variables from ConfigMaps or Secrets
- `resources`: CPU and memory requests/limits
- `liveness_probe`: Health check configuration
- `readiness_probe`: Readiness check configuration
- `security_context`: Container-level security settings

**Relationships**:
- Deployment → Container Image: References image by name:tag
- Deployment → Service: Selects pods via label selector
- Deployment → ConfigMap: Consumes non-sensitive configuration
- Deployment → Secret: Consumes sensitive data (DATABASE_URL, JWT_SECRET, OPENAI_API_KEY)

**Validation Rules**:
- Replicas MUST be >= 1
- Resource requests MUST be <= resource limits
- Liveness probe MUST be configured
- Readiness probe MUST be configured
- Security context MUST include runAsNonRoot: true
- Security context MUST include runAsUser: 1000

### 3. Kubernetes Service

**Description**: Network abstraction for pod access, defines service discovery and load balancing.

**Attributes**:
- `name`: Service name (e.g., `todo-evolution-frontend`)
- `namespace`: Kubernetes namespace (default)
- `type`: Service type (LoadBalancer for frontend, ClusterIP for backend/MCP)
- `selector`: Label selector for pods (`app: todo-evolution`, `component: <type>`)
- `ports`: List of port mappings

**Port Mapping Attributes**:
- `name`: Port name (http, https, grpc)
- `port`: Service port (external access)
- `target_port`: Container port (pod internal)
- `protocol`: TCP or UDP

**Service Discovery**:
- DNS name: `<service-name>.<namespace>.svc.cluster.local`
- Example: `todo-evolution-backend.default.svc.cluster.local:8000`

**Relationships**:
- Service → Deployment: Selects pods via label selector
- Service → Service: Services can call each other via DNS

**Validation Rules**:
- Selector MUST match pod labels
- Frontend service MUST be type LoadBalancer
- Backend/MCP services MUST be type ClusterIP
- Port MUST match container port

---

### 4. Kubernetes ConfigMap

**Description**: Non-sensitive configuration data as key-value pairs.

**Attributes**:
- `name`: ConfigMap name (e.g., `todo-evolution-config`)
- `namespace`: Kubernetes namespace (default)
- `data`: Key-value pairs of configuration

**Configuration Keys**:
- `API_BASE_URL`: Backend API base URL for frontend
- `MCP_SERVER_URL`: MCP server URL for backend
- `LOG_LEVEL`: Application logging level (INFO, DEBUG, ERROR)
- `ENVIRONMENT`: Deployment environment (development, production)

**Relationships**:
- ConfigMap → Deployment: Consumed as environment variables

**Validation Rules**:
- No sensitive data (use Secrets instead)
- All keys MUST be uppercase with underscores
- All values MUST be valid environment variable strings

---

### 5. Kubernetes Secret

**Description**: Sensitive data (passwords, API keys, tokens) with base64 encoding.

**Attributes**:
- `name`: Secret name (e.g., `todo-secrets`)
- `namespace`: Kubernetes namespace (default)
- `type`: Secret type (Opaque for generic secrets)
- `data`: Base64-encoded key-value pairs

**Secret Keys**:
- `DATABASE_URL`: PostgreSQL connection string
- `JWT_SECRET`: JWT signing secret for Better Auth
- `OPENAI_API_KEY`: OpenAI API key for MCP server

**Encoding**:
- All values MUST be base64 encoded
- Example: `postgresql://...` → `cG9zdGdyZXNxbDovLy4uLg==`

**Relationships**:
- Secret → Deployment: Consumed as environment variables (mounted from secret)

**Validation Rules**:
- MUST NOT contain secrets in plain text
- MUST be base64 encoded
- MUST NOT be committed to git (add to .gitignore)
- All secrets MUST have values before deployment

### 6. Helm Chart

**Description**: Package of Kubernetes manifests with configurable values.

**Attributes**:
- `name`: Chart name (todo-evolution)
- `version`: Semantic version (1.0.0)
- `description`: Chart description
- `api_version`: Helm API version (v2)
- `app_version`: Application version (1.0.0)

**Chart Structure**:
```
todo-evolution-chart/
├── Chart.yaml              # Chart metadata
├── values.yaml             # Default configuration values
├── values-dev.yaml         # Development environment overrides
├── values-prod.yaml        # Production environment overrides
└── templates/
    ├── _helpers.tpl        # Template helpers (labels, names)
    ├── frontend/
    │   ├── deployment.yaml
    │   ├── service.yaml
    │   └── serviceaccount.yaml
    ├── backend/
    │   ├── deployment.yaml
    │   ├── service.yaml
    │   └── serviceaccount.yaml
    ├── mcp-server/
    │   ├── deployment.yaml
    │   ├── service.yaml
    │   └── serviceaccount.yaml
    ├── secrets.yaml        # Kubernetes Secret template
    ├── configmap.yaml      # Kubernetes ConfigMap template
    └── NOTES.txt           # Post-install instructions
```

**Values Schema**:
```yaml
# Global settings
global:
  environment: development
  registry: localhost

# Frontend configuration
frontend:
  enabled: true
  replicas: 2
  image:
    repository: todo-frontend
    tag: 1.0.0
  service:
    type: LoadBalancer
    port: 80
    targetPort: 3000
  resources:
    requests:
      cpu: 100m
      memory: 128Mi
    limits:
      cpu: 500m
      memory: 512Mi

# Backend configuration
backend:
  enabled: true
  replicas: 2
  image:
    repository: todo-backend
    tag: 1.0.0
  service:
    type: ClusterIP
    port: 8000
  resources:
    requests:
      cpu: 100m
      memory: 128Mi
    limits:
      cpu: 500m
      memory: 512Mi
  env:
    DATABASE_URL:  # From secret
    JWT_SECRET:    # From secret

# MCP Server configuration
mcpServer:
  enabled: true
  replicas: 1
  image:
    repository: todo-mcp-server
    tag: 1.0.0
  service:
    type: ClusterIP
    port: 8001
  resources:
    requests:
      cpu: 100m
      memory: 128Mi
    limits:
      cpu: 500m
      memory: 512Mi
```

**Relationships**:
- Helm Chart → Deployment: Contains deployment templates
- Helm Chart → Service: Contains service templates
- Helm Chart → Secret: Contains secret templates
- Helm Chart → ConfigMap: Contains ConfigMap templates

**Validation Rules**:
- MUST pass `helm lint` validation
- All templates MUST be valid YAML
- Values.yaml MUST provide sensible defaults
- All resources MUST have standard Kubernetes labels
- All containers MUST have resource limits defined

### 7. Minikube Cluster

**Description**: Local single-node Kubernetes environment for development and testing.

**Attributes**:
- `name`: Cluster name (minikube)
- `driver`: Container driver (docker)
- `cpus`: Number of CPUs allocated (4)
- `memory`: Memory allocated in MB (8192 = 8GB)
- `disk_size`: Disk size in GB (20GB)
- `kubernetes_version`: Kubernetes version (v1.30.0)

**Add-ons**:
- `ingress`: Ingress controller for external access
- `metrics-server`: Resource metrics for autoscaling and monitoring

**Network**:
- Docker bridge network for container communication
- Service CIDR: 10.96.0.0/12
- Pod CIDR: 10.244.0.0/16

**Relationships**:
- Minikube → Deployment: Hosts all deployment resources
- Minikube → Service: Exposes services via LoadBalancer (tunnel)

**Validation Rules**:
- MUST be running before deployment
- MUST have adequate resources (4 CPUs, 8GB RAM)
- MUST use docker driver
- MUST have ingress and metrics-server enabled

## State Transitions

### Container Image Lifecycle

```
[source code] → [Gordon generates Dockerfile] → [docker build] → [image:tag] → [push to registry] → [deploy to Kubernetes]
```

**States**:
1. **Source**: Application source code exists
2. **Dockerfile Generated**: Gordon creates Dockerfile
3. **Built**: Image built locally (`todo-frontend:1.0.0`)
4. **Tested**: Image tested locally with `docker run`
5. **Tagged**: Image tagged with semantic version
6. **Deployed**: Image deployed to Minikube (load to Minikube docker daemon)

**Transitions**:
- Source → Dockerfile Generated: Gordon AI command
- Dockerfile Generated → Built: `docker build` command
- Built → Tested: `docker run` + health check
- Tested → Tagged: `docker tag` command
- Tagged → Deployed: `docker save | minikube image load` or Minikube docker-env

---

### Deployment Lifecycle

```
[manifest generated] → [kubectl apply] → [pods created] → [pods starting] → [pods ready] → [serving traffic]
```

**States**:
1. **Manifest Generated**: kubectl-ai generates YAML
2. **Applied**: `kubectl apply` or `helm install` executed
3. **Progressing**: Deployment in progress (pods being created)
4. **Ready**: All replicas ready and serving traffic
5. **Failed**: Deployment failed (pods failing, image pull errors, etc.)

**Transitions**:
- Manifest Generated → Applied: `kubectl apply -f deployment.yaml` or `helm install`
- Applied → Progressing: Kubernetes creates ReplicaSet and pods
- Progressing → Ready: Pods pass readiness probes
- Progressing → Failed: Pods fail health checks, image pull errors
- Failed → Ready: Fix issue and rollout restart

**Rolling Update**:
```
[Ready] → [new image deployed] → [new pod created] → [new pod ready] → [old pod terminated] → [Ready]
```

---

### Scaling Lifecycle

```
[stable deployment] → [kubectl scale] → [new replicas created] → [new replicas ready] → [scaled deployment]
```

**States**:
1. **Stable**: Deployment at current replica count
2. **Scaling**: Replica count changed via kubectl-ai or kubectl scale
3. **Progressing**: New replicas being created/terminated
4. **Scaled**: All desired replicas ready

**Transitions**:
- Stable → Scaling: `kubectl-ai "scale deployment to N replicas"`
- Scaling → Progressing: Kubernetes creates/terminates pods
- Progressing → Scaled: All replicas reach ready state

## Configuration Management

### Environment-Specific Values

**Development (values-dev.yaml)**:
- Replicas: 1 for each service
- Resource limits: Minimal (100m CPU, 128Mi memory)
- Log level: DEBUG
- Database: Local or development Neon instance

**Production (values-prod.yaml)**:
- Replicas: 2-3 for frontend/backend, 1 for MCP
- Resource limits: Higher (500m CPU, 512Mi memory)
- Log level: INFO
- Database: Production Neon instance with connection pooling

### Secret Management

**Creation**:
```bash
kubectl create secret generic todo-secrets \
  --from-literal=DATABASE_URL="postgresql+asyncpg://..." \
  --from-literal=JWT_SECRET="production-secret" \
  --from-literal=OPENAI_API_KEY="sk-..."
```

**Usage in Deployment**:
```yaml
env:
  - name: DATABASE_URL
    valueFrom:
      secretKeyRef:
        name: todo-secrets
        key: DATABASE_URL
```

## Glossary

- **Container Image**: Executable package containing application code and dependencies
- **Deployment**: Kubernetes resource for managing pod replicas and updates
- **Service**: Kubernetes network abstraction for service discovery
- **ConfigMap**: Non-sensitive configuration data
- **Secret**: Sensitive data (passwords, API keys) with base64 encoding
- **Helm Chart**: Package of Kubernetes manifests with configurable values
- **Minikube**: Local single-node Kubernetes cluster
- **Gordon**: Docker AI for generating Dockerfiles
- **kubectl-ai**: AI tool for generating Kubernetes manifests
- **kagent**: AI tool for cluster analysis and optimization
- **Replica**: Single instance of a pod
- **Pod**: Smallest deployable Kubernetes unit (one or more containers)
- **Liveness Probe**: Health check that restarts container if failing
- **Readiness Probe**: Health check that removes pod from service if failing
